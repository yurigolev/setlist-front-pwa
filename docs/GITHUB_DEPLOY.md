# Setlist: инструкция по CI/CD из GitHub на VPS

Актуально на 6 октября 2026 года. План рассчитан на один VPS с Ubuntu 24.04 LTS, 2 ГБ RAM и 40 ГБ SSD, два GitHub-репозитория и одну общую библиотеку.

Это исходный план подготовки, включая будущий HTTPS и ручной вариант релизов. Текущий реализованный workflow использует автоматический деплой `main` и описан в [DEPLOYMENT.md](DEPLOYMENT.md); его имена secrets и порядок запуска имеют приоритет. Приведённые ниже адреса и пути сервера — примеры; команды диагностики выполнять на выбранном VPS. Наличие инструкции само по себе не подтверждает успешный запуск сервера.

## 1. Как будет работать доставка

```text
Изменение кода → Pull Request → проверки
Merge в основную ветку → проверки → сборка Docker-образа
→ GitHub Container Registry (GHCR) → Run workflow в GitHub Actions
→ SSH на VPS → скачивание готового образа → запуск → проверка
```

Runner — машина, которая выполняет задания GitHub Actions. Registry — хранилище собранных образов. VPS только запускает готовое приложение: сборка и тесты выполняются на runner.

Для начала рекомендован автоматический CI и отдельный production-workflow с `workflow_dispatch`: кнопка `Actions → Deploy → Run workflow`. Кнопка запускает весь процесс без ручного копирования файлов. После проверки нескольких релизов её можно заменить автоматическим запуском после успешного CI основной ветки. Во время выступления релизы не запускать.

Образы фронта и API собирать отдельно. На сервере хранить manifest релиза: точные ссылки на оба образа, версии конфигурации и миграций. Теги — полный commit SHA, для запуска желательно фиксировать digest `@sha256:...`. Не использовать `latest` как источник версии production.

## 2. Что проверить до настройки

- IP нового VPS, ОС и архитектуру. Для обычного x86-64 VPS собирать `linux/amd64`; образ с ARM Mac без выбора платформы может не запуститься.
- Есть ли на сервере чужие приложения, Docker volumes или занятые порты. Существующий сервер не переустанавливать и не очищать.
- Два адреса GitHub-репозиториев: `mobile-setlist` и `setlist-back`; имя основной ветки в каждом; личный аккаунт или организация, публичные или приватные репозитории.
- Включённые GitHub Actions, доступный hosted Linux runner, остаток минут и лимиты хранения Actions/Packages на вашем тарифе; доступ к GHCR.
- Постоянный домен, например `setlist.example.ru`. Создать A-запись на IPv4 VPS. AAAA-запись добавлять только при реально настроенном IPv6.
- Доступ с VPS к `ghcr.io` и registry инфраструктурных образов. Проверить скачивание выбранных версий PostgreSQL, MinIO, Caddy и приложений до переноса данных.
- Отдельное место для резервных копий: другое хранилище или другой компьютер. Копия на том же VPS не защищает от его потери.

На VPS проверить:

```sh
cat /etc/os-release
uname -m
free -h
df -h
sudo ss -lntup
```

Если Docker уже установлен:

```sh
sudo docker version
sudo docker compose version
sudo docker ps -a
sudo docker volume ls
```

## 3. Подготовить сервер один раз

1. Сохранить доступ к консоли провайдера. Создать отдельную учётную запись администратора, добавить его публичный SSH-ключ, проверить вход и `sudo` из второго терминала. Только после этого отключить SSH-вход по паролю и прямой вход root.
2. Установить обновления ОС. Docker Engine и Compose plugin установить из официального репозитория Docker по инструкции ниже. Node.js, npm и Actions runner для работы приложения на VPS не требуются.
3. Открыть TCP 80/443 для сайта и SSH-порт для управления. SSH по возможности ограничить доверенными адресами администратора и runner; для hosted runner учитывать меняющиеся адреса. Не открывать PostgreSQL, MinIO, API и Docker daemon наружу.
4. Подготовить `/opt/setlist`, отдельный каталог состояния релизов, секретов и бэкапов. Production-секреты доступны только владельцу; права на `.env.production` — `600`.
5. При необходимости добавить 1–2 ГБ swap, проверив свободный диск. Swap страхует кратковременные пики, но не заменяет RAM. Если при обычной работе появляется постоянный swap или OOM, увеличить RAM.
6. Настроить ограничение размера Docker-логов и перезапуск сервисов после reboot, например `restart: unless-stopped`. Проверить перезагрузкой до переноса библиотеки.

Для CI создать отдельного пользователя `deploy` и отдельный SSH-ключ. Рекомендуемый доступ — запуск root-owned скрипта `/usr/local/sbin/setlist-deploy` через ограниченное правило `sudo`. Скрипт, Compose, Caddyfile и конфигурация, исполняемая с привилегиями, не должны быть доступны CI-пользователю на запись. Скрипт проверяет сервис, registry-путь и digest; не принимает произвольные команды, пути или Compose-файлы. Изменения инфраструктуры устанавливает администратор после проверки.

Членство в группе `docker` фактически даёт root-доступ. Не выдавать его CI-пользователю как будто это ограниченное разрешение. Компрометация разрешённого production-образа тоже опасна: контейнеры приложения не должны получать Docker socket, privileged mode или произвольные host mounts.

## 4. Собрать единый production Compose

Все сервисы в одном Compose-проекте `setlist-production`:

```text
Интернет → Caddy с HTTPS → Nginx с PWA → Fastify API
                                             ↓
                                      PostgreSQL + MinIO
```

Нужен новый общий production-конфиг. Переиспользовать определения PostgreSQL, MinIO, healthcheck и volumes из бэкенда; добавить PWA. В production у приложений должно быть `image:`, а не `build:`. На VPS команда `up --build` не нужна.

Что изменить относительно текущих файлов:

- В PWA собрать `VITE_API_BASE_URL` пустым: запросы идут на `/v1` того же домена. Это публичная настройка сборки, не место для секретного API-ключа.
- Для Nginx задать `BACKEND_URL=http://api:3000`; убрать зависимость от `host.docker.internal:3300`.
- Caddy направляет сайт на `pwa:80`, а `/health` — прямо на `api:3000`. Текущий Caddyfile бэкенда направляет весь домен только на API.
- `PWA_ORIGIN` — точный HTTPS-origin сайта. Один домен проще двух отдельных доменов фронта и API.
- Только Caddy публикует host-порты 80/443. У `pwa`, `api`, `postgres`, `minio` не должно быть публичных `ports:`.
- Именованные volumes сохраняют PostgreSQL, файлы MinIO и состояние HTTPS-сертификатов. Имя Compose-проекта постоянно: случайное изменение имени может создать пустые новые volumes.
- Зафиксировать проверенные версии инфраструктурных образов; PostgreSQL и MinIO не обновлять автоматически при обычном релизе приложения.
- Проверить старт PWA после пересоздания API: Nginx должен корректно работать с обновлённым адресом контейнера, при необходимости пересоздавать PWA после API.
- API сейчас без авторизации. Перед публичным запуском реализовать и проверить защиту чтения, изменения и скачивания вложений. Скрытый URL и CORS не ограничивают доступ посторонних.

Пример маршрутизации Caddy для этой схемы, после подготовки остальных файлов:

```caddyfile
{$APP_DOMAIN} {
  encode zstd gzip
  handle /health {
    reverse_proxy api:3000
  }
  handle {
    reverse_proxy pwa:80
  }
}
```

## 5. Настроить GitHub и секреты

В каждом репозитории:

1. Настроить защиту основной ветки/ruleset с обязательными проверками и Pull Request, если это доступно для видимости репозитория и вашего тарифа. Проверить, кто может менять workflows и запускать деплой. Для приватных репозиториев GitHub Free некоторые защиты недоступны: ручная кнопка не заменяет branch protection, доступ на запись должен быть только у доверенных людей.
2. В `Settings → Actions → General` проверить разрешённые Actions и настройки token permissions. Использовать hosted Linux runner, например `ubuntu-24.04`. На VPS с 2 ГБ RAM сборочный runner не размещать.
3. Сборочная job публикует образ в `ghcr.io/<owner>/<repo>` через встроенный `GITHUB_TOKEN`. Для неё явно задать `permissions: contents: read` и `packages: write`; остальным job дать только необходимые права. Имена image namespace привести к нижнему регистру. После первой публикации проверить связь package с репозиторием и его видимость; для закрытого приложения оставить package private.
4. Для скачивания приватных образов VPS создать отдельный PAT **classic** с `read:packages`, сроком действия и доступом к обоим packages. При необходимости авторизовать SSO организации. Серверу не выдавать write/delete packages или административные права. Токен хранить на VPS в защищённом Docker credential config/credential helper того пользователя, который выполняет pull; использовать `docker login ghcr.io --password-stdin`. `GITHUB_TOKEN` job не подходит как постоянный серверный пароль. Если образы публичные, anonymous pull возможен, но это отдельное решение о публикации содержимого.
5. Секретные пароли PostgreSQL и MinIO хранить на VPS, вне Git. Не переносить их в браузерные `VITE_*`, Docker build args, артефакты или логи pipeline.

Настройки deploy-workflow в `Settings → Secrets and variables → Actions`:

| Переменная | Тип | Значение |
| --- | --- | --- |
| `DEPLOY_HOST` | Variable | IP или SSH-hostname VPS |
| `DEPLOY_PORT` | Variable | SSH-порт |
| `DEPLOY_USER` | Variable | Пользователь `deploy` |
| `SSH_PRIVATE_KEY` | Secret | Отдельный многострочный приватный ключ CI |
| `SSH_KNOWN_HOSTS` | Secret | Заранее проверенная запись host key VPS |

Если ваш тариф поддерживает environments для этих репозиториев, создать `production`, ограничить deployment branches основной веткой, использовать environment secrets и `environment: production` в deploy-job. Если environments недоступны, использовать repository secrets и явно проверять допустимую ветку в workflow. Required reviewers тоже зависят от тарифа и видимости репозитория; базовый путь инструкции — отдельный ручной workflow, который не требует этой функции.

Job получает SSH-ключ из Secret через переменную окружения и записывает его во временный файл с правами `600`, затем удаляет файл. Многострочный ключ сохранить с переводами строк, включая LF после последней строки. Ключ не печатать и shell trace не включать. Маскирование логов не заменяет ограничение доступа. Секреты использовать только в deploy-job доверенного workflow; PR-проверкам они не нужны. Не запускать недоверенный PR-код через `pull_request_target` с production-секретами.

Host key сверить через доверенную консоль провайдера, затем сохранить запись для того адреса и порта, по которым подключится CI. Не использовать `StrictHostKeyChecking=no` и не получать host key вслепую через `ssh-keyscan` во время job.

## 6. Подготовить pipeline обоих проектов

В каждом репозитории создать `.github/workflows/ci.yml` для `test → build/publish` и `.github/workflows/deploy.yml` для ручного деплоя. На hosted Linux runner использовать Docker Buildx, `docker/login-action` и `docker/build-push-action`; отдельный Docker-in-Docker daemon обычно не нужен. Сторонние Actions фиксировать проверенным полным commit SHA и обновлять осознанно.

Ручной deploy-workflow должен находиться в default branch. Пользователь выбирает SHA успешно собранного релиза; job проверяет его принадлежность основной ветке, успешные CI-проверки и соответствующий опубликованный digest. Нельзя разрешать запуск произвольного образа только потому, что его адрес ввели в поле. Недоверенные inputs передавать через env с проверкой формата, не вставлять напрямую в shell-код.

### Фронт

- Проверки: `npm ci`, `npm run test`, `npm run build` на Node.js 24.
- Сборка production Docker-образа из существующего Dockerfile с пустым `VITE_API_BASE_URL`, под архитектуру VPS.
- Публикация образа в GHCR с тегом `${{ github.sha }}`, сохранение digest в метаданных workflow.

### Бэкенд

- Проверки: `npm ci`, `npm run typecheck`, `npm run build`, `npm run db:check`, `npm test`.
- Для `npm test` нужны отдельные тестовые PostgreSQL, MinIO и запущенный API. Настроить тестовые env, миграции и ожидание готовности API. Тест PostgreSQL создаёт временную БД: тестовая роль должна иметь нужные права.
- Тесты запускаются в изолированном CI-окружении. Они создают и удаляют песни; production URL и production-секреты им не передавать.
- Собрать и опубликовать backend-образ с тегом `${{ github.sha }}`, сохранить digest.

### Общие правила

- Проверки выполнять на `pull_request` и `push` основной ветки. Образы публиковать только после успешных проверок доверенного кода основной ветки. Production-деплой — только для проверенного опубликованного релиза.
- На старте deploy запускается через `workflow_dispatch`, со строгой проверкой основной ветки. Если используется environment, указать `production`.
- `concurrency: group: production` с `cancel-in-progress: false` сериализует деплои внутри одного репозитория. Он не блокирует job второго репозитория: серверный deploy-скрипт дополнительно использует общий `flock` для обоих сервисов и бэкапов.
- Не включать автоматическую отмену job, которая уже меняет production. Перед применением проверять актуальность релиза: старый отложенный запуск не должен случайно заменить новый; намеренный rollback оформить отдельным явно выбранным действием. GitHub concurrency не гарантирует порядок очереди.
- При изменении API-контракта заранее определить совместимую пару версий фронта и API. Для несовместимых изменений нужен согласованный релиз обоих сервисов, а не два произвольных независимых обновления.

## 7. Что должен делать серверный deploy-скрипт

Скрипт ещё предстоит подготовить. Его последовательность:

1. Проверить аргументы, архитектуру, свободное место и получить общую блокировку деплоя/бэкапа.
2. Записать предыдущий manifest: digest PWA, digest API и версию production-конфига. При обновлении одного сервиса сохранить проверенную версию второго.
3. Скачать новый образ до остановки работающего приложения. Ошибка registry не должна выключать старую версию.
4. Перед backend-релизом сделать согласованную копию PostgreSQL и MinIO, проверить завершение копирования во внешнее хранилище. При ошибке обязательного бэкапа остановить релиз.
5. Выполнить проверку Compose без вывода раскрытых секретов, применить миграции по выбранной схеме и запустить нужные версии. Текущий Dockerfile API уже выполняет миграции при каждом старте — это поведение нужно учитывать или вынести в отдельную migration-job.
6. Дождаться healthcheck PostgreSQL, MinIO, API и готовности PWA с ограниченным timeout. Проверить внешние HTTPS `/health` и главную страницу.
7. Проверить ожидаемый формат ответа `/health`, а не только HTTP 200: SPA fallback может вернуть HTML на неизвестный путь.
8. После успеха записать новый manifest как текущий. При ошибке сохранить логи без секретов, пометить job как failed и применить предусмотренный план отката.

Это обычный Compose-деплой с возможной короткой паузой при пересоздании API и миграциях. Нулевой downtime эта схема не обещает. Бэкап текущим скриптом тоже временно останавливает API.

## 8. Первый перенос библиотеки

1. Закончить редактирование библиотеки на Mac. Снять свежий полный бэкап штатным `scripts/backup.sh` бэкенда и успешно проверить `scripts/verify-restore.sh` в изолированном окружении.
2. Копировать весь каталог: `postgres.dump`, `objects/manifest.json` и файлы вложений. Сохранить дополнительную копию вне нового VPS.
3. Подготовить новую production-связку с постоянными volumes, секретами и нужной парой образов. Не допускать пользовательских записей во время восстановления.
4. Восстановить PostgreSQL и MinIO в production volumes. Готового скрипта восстановления постоянного production-проекта сейчас нет: подготовить его и проверить на временном окружении до переноса.
5. Проверить миграции, ревизию библиотеки, число песен, вложения и контрольные суммы. Подключить домен и убедиться, что HTTPS и авторизация работают.
6. Открыть новый домен на каждом телефоне, выполнить полную синхронизацию и установить PWA с нового адреса. Новый origin имеет отдельное браузерное хранилище: копия со старого tunnel-домена автоматически не переносится.
7. Проверить изображения, MP3, поиск и запуск в авиарежиме. Сохранить исходную библиотеку и бэкап Mac до завершения проверки всех устройств.

Текущие backup-скрипты вызывают обычный `docker compose` и ориентируются на локальную конфигурацию. Перед использованием на VPS адаптировать их к точному Compose-файлу, env-файлу и имени production-проекта. `verify-restore.sh` должен всегда работать с отдельными временными volumes и ограниченным тестовым окружением; дополнительный полный стек на VPS с 2 ГБ может не поместиться. Проверку восстановления выполнять на отдельной машине/runner с достаточными ресурсами.

## 9. Как пользоваться после настройки

Обычный релиз: создать Pull Request → дождаться зелёных проверок → merge → дождаться опубликованного образа → `Actions → Deploy → Run workflow`, выбрать SHA релиза → дождаться проверки → открыть приложение на телефоне и обновить библиотеку.

Откат приложения: выбрать предыдущий manifest и запустить повторный deploy точных прежних образов. Старые образы и manifests сохранять как минимум для нескольких последних проверенных релизов; исключить их из registry cleanup.

Миграции должны быть совместимы с предыдущим кодом, если нужен быстрый откат. Возврат старого Docker-образа не отменяет изменение БД. После несовместимой миграции нужен отдельный план восстановления или исправления. Восстановление бэкапа может потерять записи после момента его создания; выполнять его только после оценки этих записей и явного решения о восстановлении.

Не выполнять `docker compose down -v` или очистку volumes в production. Эти команды удалят библиотеку. Перезапуск и обновление приложения должны сохранять volumes.

## 10. Что проверить после запуска

- Без авторизации нельзя читать библиотеку, менять песни или скачивать вложения.
- HTTPS действителен, HTTP перенаправляется на HTTPS, домен постоянный.
- Снаружи не доступны 3000, 5432, 9000/9001 и Docker daemon.
- Перезагрузка VPS возвращает приложение в рабочее состояние; песни и файлы сохраняются.
- Failed test не допускает deploy; failed deploy отображается красным, одновременные релизы не пересекаются.
- Работают внешние бэкапы по расписанию и уведомление о сбое бэкапа.
- Есть проверенный откат предыдущего приложения и проверенное восстановление данных.
- Есть контроль `/health`, свободного диска, RAM/OOM и баланса VPS. Настройка выбранного сервиса уведомлений — отдельный шаг.
- Все телефоны проверены в авиарежиме перед выступлением.
