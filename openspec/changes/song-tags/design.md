## Context

Мотивация описана в proposal.md. Backend использует PostgreSQL/Drizzle, songs.library_id, scoped API, блокировку строки библиотеки, song.revision и library.revision. Клиент Vue/Pinia публикует целый подтверждённый снимок IndexedDB после проверки вложений; поиск и фильтр плейбэка локальные. Запись требует online owner/editor. Копирование песен уже реализовано между сет-листами.

## Goals / Non-Goals

**Goals:** добавить теги в существующее сохранение, права и атомарные снимки; обеспечить множественный выбор и фильтрацию по любому выбранному тегу; сохранить совместимость старых запросов и кэша.

**Non-Goals:** отдельные ревизии тегов, журнал изменений, категории/иерархия, автоклассификация, офлайн-редактирование и серверная пагинация.

## Decisions

1. `tags(id, library_id, name, normalized_name, color)` и `song_tags(library_id, song_id, tag_id)`. Уникальность названия внутри библиотеки; PK тройки library/song/tag и обратный индекс library/tag. Составные FK по library/id исключают межбиблиотечные связи. Это сохраняет единое переименование, в отличие от строковых массивов в песнях.
2. Нормализация: Unicode NFC, обрезка и схлопывание пробелов, lowercase ru для ключа. Показываем исходный регистр нормализованного имени; ограничение 1–40 символов. Никаких tag.revision или timestamps; последнее сохранение имени побеждает.
3. CRUD `/v1/setlists/:setlistId/tags`, создание принимает `{name, color?}`, PATCH — непустой объект с необязательными `name` и `color`, список возвращает `{tags}`, создание/обновление — `{id,name,color}`. Цвет — nullable HEX `#RRGGBB`, сервер нормализует его к верхнему регистру; отсутствие цвета в PATCH сохраняет его, `null` снимает. Song DTO содержит `tagIds`; создание и PATCH принимают массив. PATCH без поля сохраняет связи. Набор уникальных ID сортируется для идемпотентности. Каждая операция проверяет scope/роль; изменения сериализуются существующей блокировкой библиотеки.
4. Назначение обновляет текущие song/library revision. Переименование и изменение цвета меняют только library revision; удаление снимает назначения и увеличивает версии затронутых песен. Поля песни и связи меняются одной транзакцией.
5. Снимок содержит общий `tags[]`, песни — `tagIds[]`. На клиенте справочник хранится в существующей транзакции снимка, без отдельного независимого обновления. Отсутствующие поля старого кэша приводятся к пустым массивам. Store очищает теги при смене пользователя/сет-листа и отзыве доступа.
6. Локальная фильтрация ANY (хотя бы один выбранный тег) без переключателя условий сочетается с текущими text/audio условиями. Форма показывает существующие теги теми же крупными чипсами, что и настройки: нажатие переключает назначение, выбранный чип подсвечен и имеет aria-pressed. Все теги показываются сразу, без поиска и сворачивания. Панель фильтра библиотеки не содержит заголовка и счётчика выбранных тегов; при выборе появляется чип «Сбросить» и число найденных песен. Просмотр песни показывает назначенные крупные чипсы без действий; библиотека — панель фильтра. Справочник создаётся и редактируется в разделе «Теги» настроек сетлиста: owner видит разделы «Общее», «Теги», «Доступ» (участники и приглашения вместе), editor — только теги. При открытии настроек и смене scope загружается соответствующий снимок песен и тегов. На странице настроек отображаются только крупные чипсы и кнопка добавления; создание, переименование и подтверждение удаления происходят в одной модалке. Универсальный AppTag без зависимости от store используется для управления, переключения выбора и статичного отображения в просмотре песни и списке. Чипсы настроек открывают модалку целиком, без отдельного троеточия. Финальные отступы крупных тегов: 12px 22px на desktop и 10px 18px на mobile; высоты 56px и 48px. В модалке доступны палитра из 12 цветов, лениво загружаемый ChromePicker из `vue-color`, HEX и «Без цвета». Новый тег получает предложение наименее используемого цвета палитры на клиенте; существующий бесцветный остаётся нейтральным. Цвет применяется во всех представлениях AppTag. Предпросмотр не записывает изменения до сохранения.
7. Копирование сопоставляет нормализованные имена в целевой библиотеке, создаёт недостающие с исходным цветом и назначает целевые ID в существующей транзакции копирования. Существующий целевой тег сохраняет свой цвет.

## Risks / Trade-offs

- Старый клиент может отправить PATCH без тегов → сохраняем связи; новые поля добавляются совместимо.
- Устаревшая форма с удалённым тегом → проверка song revision и существования каждого ID исключает восстановление.
- Последнее переименование может заменить параллельное → это согласованное упрощение без отдельной ревизии.
- Изменения двух репозиториев → контракт согласован между агентами, интеграционный агент проверяет их вместе.
- Существующие локальные данные → проверка сначала в отдельной QA БД, затем только аддитивная миграция рабочего локального стека без очистки томов.

## Migration Plan

Сгенерировать и проверить аддитивную миграцию, выполнить тесты на одноразовой БД, затем обновить локальный backend и frontend. Сначала выпускать backend, после — клиент. При откате приложения новые таблицы сохраняются, старые клиенты игнорируют новые поля. Dev-окружение оставить запущенным для проверки пользователем.
