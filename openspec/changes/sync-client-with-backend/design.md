## Context

Исходный MVP хранил `Song`, вложения и Blob локально. Этот change уже перевёл подтверждённые изменения на backend, а IndexedDB использует как полную копию серверной библиотеки. Backend change `add-offline-sync-backend` в соседнем `setlist-back` реализован; его `openapi.yaml` и `/openapi.yaml` задают API одной публичной библиотеки и полного снимка. Состояние production-развёртывания на 2026-10-06 зафиксировано ниже; исходные проектные решения не являются доказательством проверки нового HTTPS-origin.

## Goals / Non-Goals

**Goals:**

- Сохранить одну форму и кнопку «Сохранить», при которой все подтверждённые операции отражаются в серверном снимке.
- Использовать IndexedDB только как копию подтверждённых данных и файлов для офлайн-чтения.
- Переживать ошибку сети, квоты или одного файла без ложного статуса полного сохранения.

**Non-Goals:**

- Офлайн-редактирование, outbox, пользовательские аккаунты и импорт тестовой базы с временного origin.
- Атомарная транзакция одного нажатия формы через PostgreSQL и MinIO: операции формы могут подтвердиться частично.

## Decisions

### Контракт с backend

Клиент следует `setlist-back/openapi.yaml`: `POST /v1/songs`, `PATCH` и `DELETE /v1/songs/:id`, `GET /v1/library/snapshot`, `POST /v1/songs/:songId/attachments`, `DELETE /v1/attachments/:id` и `GET /v1/attachments/:id/content`. Базовый URL API задаётся через публичную конфигурацию сборки без секретов; относительный `contentUrl` из снимка разрешается относительно этого URL, а не origin PWA. Ответ снимка содержит `libraryId`, `libraryRevision`, песни с `revision` и вложения с `id`, `mimeType`, `filename`, `byteSize`, `checksum`, `contentUrl`.

Существующее поле клиента `content` соответствует серверному `notes`, а `Attachment.name` — `filename`. Это сопоставление выполняется явно в адаптере API; массив `attachments` в текстовый запрос не попадает. Сервер требует непустые `title` и `artist`, поэтому форма проверяет оба поля до отправки; пустые заметки передаются как `notes: ''`. UUID и ревизия сервера становятся частью клиентской модели; `fileKey` остаётся локальным ключом Blob и не отправляется на сервер. `POST /v1/songs` получает `Idempotency-Key` одной логической попытки, `PATCH` и `DELETE` — `If-Match` с известной ревизией песни. Загрузка передаёт один multipart-файл в поле `file`, стабильный `X-Attachment-Id` и `If-Match`; повтор того же файла использует прежние id и ревизию запроса. Допустимы PNG, JPEG, WebP до 10 МиБ и MP3 до 50 МиБ в текущем развёртывании; файл с пустым MIME, распознанный по `.mp3`, отправляется с `audio/mpeg`.

Раздельные HTTP-запросы нужны из-за потоковой передачи MP3 и отдельного повтора файла. Пользователь сохраняет форму одной кнопкой, включая выбор вложений при создании новой песни. Клиент выполняет текстовую операцию, затем удаляет старые и загружает новые файлы. Успешное добавление или удаление вложения увеличивает ревизию песни на сервере, но ответ маршрута вложения не содержит новую ревизию: перед следующим upload клиент получает снимок и берёт из него актуальную ревизию. После каждого подтверждённого шага он получает снимок, даже если следующий шаг завершился ошибкой. При частичном успехе форма показывает подтверждённое и оставшееся действие, сохраняя файл и id для повтора. Замена MP3 удаляет прежний файл до загрузки нового; промежуточное отсутствие MP3 отражается честно.

Серверные ошибки имеют `code`, `message`, `requestId`; конфликт `409 REVISION_CONFLICT` содержит `currentRevision`. `428` означает отсутствие корректного `If-Match`, `413`/`415` — неподходящий файл. При потере ответа на создание или upload клиент сверяет снимок и повторяет тот же запрос с прежним ключом или attachment id; новый ключ создаётся только для новой логической операции. Для ответа с неясным результатом на `PATCH` или `DELETE` сначала запрашивается снимок, без слепого автоматического повтора. При конфликте обновляется подтверждённое состояние, а несохранённый текст формы сохраняется для решения пользователя.

### Состояние IndexedDB

Схема хранит серверные песни, файлы и метаданные `libraryId`, `libraryRevision`, время обновления и маркер завершённого серверного снимка. Клиент переиспользует файл с тем же ключом UUID/checksum, скачивает отсутствующие файлы через API и проверяет `byteSize` и SHA-256. Новые проверенные байты записываются в файловый store до публикации метаданных, а их ключи отслеживаются для очистки при ошибке; отдельного staging store или физического переноса Blob между stores нет. После загрузки всех файлов одной транзакцией IndexedDB публикуются песни и revision, удаляются ненужные files и записывается complete marker. При сбое новые скачанные ключи очищаются, предыдущий подтверждённый снимок остаётся пригодным. Service Worker не подменяет серверный снимок или content-ответы собственным runtime-кэшем: офлайн-источником остаётся завершённая копия IndexedDB.

Текущая база на временном origin считается тестовой. На постоянном origin клиент получает первичную библиотеку с backend. Если в том же origin есть старая локальная база, до первого серверного снимка её нельзя считать серверной копией: она отделяется маркером версии источника и не отправляется на backend автоматически.

### Работа без сети и ошибки

На старте клиент показывает последнюю завершённую копию сразу и при наличии сети обновляет её. Ручная кнопка повторяет обновление. При отсутствии сервера создание/редактирование/удаление блокируются сообщением «Для сохранения требуется интернет», но поиск, картинки и MP3 остаются доступны. Ошибка `If-Match` показывает конфликт и актуальное состояние без автоматического повтора старой правки.

## Risks / Trade-offs

- [Текст сохранён, файл не загрузился] -> форма показывает частичный успех, обновляет снимок и предлагает повтор файла.
- [Сервер подтвердил запись, ответ потерялся] -> клиент сверяет снимок; create/upload повторяются с тем же ключом или id.
- [Ошибка загрузки или квота IndexedDB] -> старая завершённая копия остаётся доступной, новый снимок не маркируется завершённым.
- [API публичен] -> клиент не хранит секретов для доступа; авторизация добавляется отдельным этапом.

## Migration Plan

1. Использовать готовый OpenAPI и работающий backend из `add-offline-sync-backend`.
2. Расширить доменную модель и IndexedDB-схему без автоматической отправки старых локальных записей.
3. Перевести форму и вложения на запись через API, затем включить обновление снимка.
4. Проверить на двух устройствах запись, ручное обновление, конфликт и запуск в авиарежиме.

### Схема работы и доставка

```text
Браузер → HTTP:80 → frontend (nginx)
                       ├─ статика Vue/Vite
                       └─ /v1 и /health → api:3000 (Fastify)
                                              ├─ PostgreSQL:5432
                                              └─ MinIO:9000
```

В production `VITE_API_BASE_URL` пустой. Nginx использует `BACKEND_URL=http://api:3000`, динамический Docker DNS и проксирует `/health` к настоящей готовности API. PostgreSQL и MinIO не имеют опубликованных host-портов. Production Compose, deploy-скрипт и бэкапы находятся в backend-репозитории; подробный эксплуатационный контекст хранится в его change `add-offline-sync-backend`.

`.github/workflows/frontend.yml`: PR проверяет код; push в `main` или ручной запуск `main` проверяет код, собирает Linux amd64 образ на GitHub-hosted runner, публикует `ghcr.io/yurigolev/setlist-front-pwa:<40-character SHA>` и вызывает по SSH `sudo /usr/local/sbin/setlist-deploy frontend <SHA>`. Actions закреплены полными commit SHA. Перед деплоем workflow сверяет SHA с текущим `main` и пропускает устаревший запуск. Два репозитория имеют свои очереди, а серверный `flock` сериализует деплои и бэкапы. Сервер не запускает npm build. Образ backend публикуется аналогично.

Variables обоих репозиториев: `DEPLOY_HOST=135.106.172.166`, `DEPLOY_USER=setlist-deploy`, `DEPLOY_PORT=22`. Secrets: `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. Значения ключей/паролей не записываются в спеки или Git. Пакеты GHCR при приёмке доступны для anonymous pull.

Текущие локальные Docker volumes PostgreSQL и MinIO были источником свежего снимка. API кратко остановлен на время согласованного backup; PostgreSQL сохранён в `postgres.dump`, объекты — вместе с manifest и SHA-256. Старый backup от 25 сентября не использован: он содержал меньше данных.

Снимок при переносе: `libraryRevision=193`, 43 активные песни, 57 вложений, 252 581 634 байта объектов. Локальная приватная копия: `/Users/1g/Backups/setlist-migration-2026-10-06`; серверная: `/opt/setlist/backups/setlist-migration-2026-10-06`. Исходные local volumes сохранены. Восстановление свежего backup в отдельный временный стек прошло; затем данные восстановлены в production и проверены по размерам и SHA-256 всех объектов. Записи, существующие только в старом IndexedDB и не подтверждённые backend, этой процедурой не импортируются.

### Исправления, необходимые для HTTP

На публичном HTTP-origin `crypto.subtle` отсутствует. При первой проверке возникла ошибка `Cannot read properties of undefined (reading 'digest')`. Теперь `sha256Hex` использует нативный Web Crypto в защищённом контексте и настоящий SHA-256 из закреплённого `@noble/hashes@2.4.0` в HTTP-контексте. Проверка целостности не отключена. Проверены известный digest, обе ветки вычисления, отклонение повреждённого вложения и сохранение предыдущего снимка. UUID уже имел fallback.

Первичная синхронизация скачивает все отсутствующие 57 вложений (~253 МБ); библиотека публикуется только после завершения. Это занимает несколько минут. Пока первой завершённой копии нет, список может выглядеть пустым с индикатором обновления; не создавать дубликаты и не считать этот промежуточный экран потерей server data. Повторное обновление переиспользует подтверждённые файлы.

HTTP допускает работу открытой страницы и IndexedDB, но не подтверждает готовность установленной PWA/service worker/офлайн-оболочки на телефоне. Полноценная production-проверка офлайн-запуска должна быть выполнена после HTTPS.

4. Обновить deploy healthcheck и docs так, чтобы проверялся действительный HTTPS/API ответ, а редирект сам по себе не считался готовностью. Сохранить работающие Actions и бэкапы.
