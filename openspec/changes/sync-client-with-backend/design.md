## Context

Сейчас `Song` содержит вложения внутри записи, а `IndexedDbSongRepository` и `IndexedDbAttachmentFileRepository` записывают изменения локально. `SongFormView` одной кнопкой сохраняет текст, удаляет старые Blob и добавляет новые. Backend change `add-offline-sync-backend` в соседнем `setlist-back` уже реализован; его `openapi.yaml` и `/openapi.yaml` задают API одной публичной библиотеки и полного снимка.

## Goals / Non-Goals

**Goals:**

- Сохранить одну форму и кнопку «Сохранить», при которой все подтверждённые операции отражаются в серверном снимке.
- Использовать IndexedDB только как копию подтверждённых данных и файлов для офлайн-чтения.
- Переживать ошибку сети, квоты или одного файла без ложного статуса полного сохранения.

**Non-Goals:**

- Офлайн-редактирование, outbox, пользовательские аккаунты и импорт тестовой базы с временного origin.
- Атомарная транзакция одного нажатия формы через PostgreSQL и MinIO: операции формы могут подтвердиться частично.

## Decisions

### Контракт с backend

Клиент следует `setlist-back/openapi.yaml`: `POST /v1/songs`, `PATCH` и `DELETE /v1/songs/:id`, `GET /v1/library/snapshot`, `POST /v1/songs/:songId/attachments`, `DELETE /v1/attachments/:id` и `GET /v1/attachments/:id/content`. Базовый URL API задаётся через публичную конфигурацию сборки без секретов; относительный `contentUrl` из снимка разрешается относительно этого URL, а не origin PWA. Ответ снимка содержит `libraryId`, `libraryRevision`, песни с `revision` и вложения с `id`, `mimeType`, `filename`, `byteSize`, `checksum`, `contentUrl`.

Существующее поле клиента `content` соответствует серверному `notes`, а `Attachment.name` — `filename`. Это сопоставление выполняется явно в адаптере API; массив `attachments` в текстовый запрос не попадает. Сервер требует непустые `title` и `artist`, поэтому форма проверяет оба поля до отправки; пустые заметки передаются как `notes: ''`. UUID и ревизия сервера становятся частью клиентской модели; `fileKey` остаётся локальным ключом Blob и не отправляется на сервер. `POST /v1/songs` получает `Idempotency-Key` одной логической попытки, `PATCH` и `DELETE` — `If-Match` с известной ревизией песни. Загрузка передаёт один multipart-файл в поле `file`, стабильный `X-Attachment-Id` и `If-Match`; повтор того же файла использует прежние id и ревизию запроса. Допустимы PNG, JPEG, WebP до 10 МиБ и MP3 до 50 МиБ в текущем развёртывании; файл с пустым MIME, распознанный по `.mp3`, отправляется с `audio/mpeg`.

Раздельные HTTP-запросы нужны из-за потоковой передачи MP3 и отдельного повтора файла. Пользователь сохраняет форму одной кнопкой, включая выбор вложений при создании новой песни. Клиент выполняет текстовую операцию, затем удаляет старые и загружает новые файлы. Успешное добавление или удаление вложения увеличивает ревизию песни на сервере, но ответ маршрута вложения не содержит новую ревизию: перед следующим upload клиент получает снимок и берёт из него актуальную ревизию. После каждого подтверждённого шага он получает снимок, даже если следующий шаг завершился ошибкой. При частичном успехе форма показывает подтверждённое и оставшееся действие, сохраняя файл и id для повтора. Замена MP3 удаляет прежний файл до загрузки нового; промежуточное отсутствие MP3 отражается честно.

Серверные ошибки имеют `code`, `message`, `requestId`; конфликт `409 REVISION_CONFLICT` содержит `currentRevision`. `428` означает отсутствие корректного `If-Match`, `413`/`415` — неподходящий файл. При потере ответа на создание или upload клиент сверяет снимок и повторяет тот же запрос с прежним ключом или attachment id; новый ключ создаётся только для новой логической операции. Для ответа с неясным результатом на `PATCH` или `DELETE` сначала запрашивается снимок, без слепого автоматического повтора. При конфликте обновляется подтверждённое состояние, а несохранённый текст формы сохраняется для решения пользователя.

### Состояние IndexedDB

Новая версия схемы добавляет метаданные `libraryId`, `libraryRevision`, время обновления, маркер серверного источника и временную область для скачанных Blob. Во время обновления клиент сравнивает attachment id/checksum с локальной копией, скачивает только новые или изменённые файлы через API и проверяет `byteSize` и SHA-256. Одной транзакцией IndexedDB он переносит проверенные Blob в активное хранилище, публикует песни, вложения и ревизию, а также убирает отсутствующие в снимке записи. Ранее скачанные файлы удаляются лишь после публикации новой версии. При сбое временные данные очищаются, предыдущий снимок остаётся пригодным. Service Worker не подменяет серверный снимок или content-ответы собственным runtime-кэшем: офлайн-источником остаётся завершённая копия IndexedDB.

Текущая база на временном origin считается тестовой. На постоянном origin клиент получает первичную библиотеку с backend. Если в том же origin есть старая локальная база, до первого серверного снимка её нельзя считать серверной копией: она отделяется маркером версии источника и не отправляется на backend автоматически.

### Работа без сети и ошибки

На старте клиент показывает последнюю завершённую копию сразу и при наличии сети обновляет её. Ручная кнопка повторяет обновление. При отсутствии сервера создание/редактирование/удаление блокируются сообщением «Для сохранения требуется интернет», но поиск, картинки и MP3 остаются доступны. Ошибка `If-Match` показывает конфликт и актуальное состояние без автоматического повтора старой правки.

## Risks / Trade-offs

- [Текст сохранён, файл не загрузился] -> форма показывает частичный успех, обновляет снимок и предлагает повтор файла.
- [Сервер подтвердил запись, ответ потерялся] -> клиент сверяет снимок; create/upload повторяются с тем же ключом или id.
- [Ошибка загрузки или квота IndexedDB] -> старая завершённая копия остаётся доступной, новый снимок не маркируется завершённым.
- [API публичен] -> клиент не хранит секретов для доступа; авторизация добавляется отдельным этапом.

## Migration Plan

1. Использовать готовый OpenAPI и работающий backend из `add-offline-sync-backend`.
2. Расширить доменную модель и IndexedDB-схему без автоматической отправки старых локальных записей.
3. Перевести форму и вложения на запись через API, затем включить обновление снимка.
4. Проверить на двух устройствах запись, ручное обновление, конфликт и запуск в авиарежиме.
